# 需求评审工作台：快速上手

这份工作台用来把“孩子完成一次运动”讲清楚，并让团队确定怎么做。它不是运动演示程序，也不会连接真实设备。

## 先花3分钟看懂

打开《运动伙伴需求评审工作台_单文件.html》，左侧选“先看完整流程”。点击八个步骤，从“家长布置任务”看到“家长查看结果”。

每一步只先看五件事：用户怎么操作、软件要做到什么、需要什么硬件、为什么这样选、现在要讨论什么。想核对实现时，再展开“方案比较、技术要求与测试方法”。第一次不用逐个记编号。

已有UE和小程序手机端初步确定，沿用已有任务操作。页面中的“推荐”仍是讨论建议；模拟数据和示例数字不代表真实设备成绩。

## 开会时这样讲，约5分钟

可以直接照着下面说，并依次点击对应步骤：

1. **先交代已有基础。**“手机端已经初步确定，家长选动作、次数、周期和提醒时间，再发送给设备。我们今天主要补齐设备怎么执行。”
2. **讲孩子如何开始。**“孩子选任务后先站好。设备用方向图标和短语音提示；如果孩子刚按完机身键，要先让他回位，站好后再倒计时。”
3. **讲计数与暂停。**“完整有效动作才加一。做到12次暂停，继续后的下一次应该是13次。断网不应打断已经收到任务的本地运动。”
4. **讲结果如何保住。**“建议先把成绩可靠存到设备，再上传。保存成功、等待同步和同步完成要分开显示。实时进度是否需要，另外决定。”
5. **收束到要决定的事。**“今天需要确定孩子怎么操作、屏幕和语音用什么形式、计数怎样算通过，以及断电允许损失多少进度。每个问题都要留下结论或下一步验证任务。”

不要把所有功能和技术表逐行念完。讲完一条运动主线后，只展开当天要决定的部分。

## 左侧五个入口分别做什么

| 入口 | 什么时候用 |
|---|---|
| 先看完整流程 | 了解整条运动链路；对比操作形式及软硬件影响 |
| 功能清单与依据 | 回查PRD；记录11月15日纳入/延期建议、承接人和理由 |
| 每一步怎么做 | 检查开始、暂停、恢复和异常处理是否完整 |
| 需要讨论的问题 | 比较方案，记录倾向和还缺什么证据 |
| 怎么证明做完了 | 看开发阶段、通过条件与测试证据；判断是否真的完成 |

R是原有需求编号，D和OPEN是待讨论问题编号；需要追溯时再看，不必在汇报中念出来。

## 讨论一个问题的最小做法

例如讨论“孩子站在远处怎样暂停”：

1. 在主流程点击“暂停、异常与恢复”，先说清楚实际使用场景。
2. 展开比较：机身键、远距手势、语音分别方便在哪里，又增加什么成本。
3. 进入“需要讨论的问题”，找到对应问题，记录倾向、理由、承接人以及下一步。没有测试证据时写“待验证”，不要写“已通过”。
4. 约定谁验证、何时反馈、什么现象算通过。比如运动动作不能误触发暂停，孩子必须能完成继续操作。

会议结束至少留下：选了什么、为什么、谁负责、什么时候确认、怎么验证。尚不能决定的，留下验证任务。

## 保存与分享

填写评审意见后点击对应的“保存”按钮。结束前到“功能清单与依据”点击“导出评审草稿”，会下载一份JSON文件；下次点击“导入评审草稿”继续。

**刷新或关闭会丢失未导出的意见。**“保存草稿”只保存在当前页面运行期间，不会修改原始PRD，也不等于团队正式批准。

分享时发送单文件HTML；需要让别人接着看你的意见，再附上导出的JSON。HTML内置的资料是打包时的快照，源文件更新后需要重新打包。外部参考网站需要联网。
