# 专业需求基线与可视化评审方法研究

调研日期：2026-10-10。用途：为现有需求和状态工作台选择评审方法；不是团队批准的需求基线，也不是实机验收报告。

## 1. 结论与适用边界

本项目应把可视化从“页面或状态图册”扩展为可追踪的需求评审工作台：同一项需求可以向上找到PRD来源，向下找到设备状态、接口/硬件影响、11月15日演示范围和验收证据。需求是否批准、实现是否完成、验证是否通过必须分开表示。

以下分为“来源做法”和“项目应用建议”。NASA的流程面向其系统工程环境，不能将NASA评审节点、委员会或全部文档负担直接套到本项目；SEBoK是工程知识体系，SCXML是状态机规范，C4与ADR是建模/记录实践。本项目采用它们支持的追踪、行为语义和证据原则，裁剪组织形式。

## 2. 来源做法：专业开发怎样连接需求与实现

### 2.1 需求先表达可验证的结果，再评估方案

NASA系统设计章节把利益相关者期望、技术需求、逻辑分解与设计方案区分开，要求需求可行、可验证且一致。需求应描述需要达到的结果，设计方案用于回答如何实现；硬性设计约束应明确其来源，不能把候选方案悄悄写成要求。[NASA §4 系统设计](https://www.nasa.gov/reference/4-0-system-design-processes/)

**项目应用建议：**“已同步任务断网仍可计数”是产品行为；“使用某主控/NPU”是实现候选。“示范视频本地缓存”只有团队做出决定后才是设计约束。11月15日范围是一份交付切片，不改变PRD完整范围本身。

### 2.2 基线是约定版本，变更要留记录

NASA技术管理章节把基线定义为某时点经约定的配置描述；改变基线涉及提出、说明、评估、批准、实施和验证。需求管理同时维护来源、分配关系与设计/测试的一致性。[NASA §6.2、§6.5](https://www.nasa.gov/reference/6-0-crosscutting-technical-management/)

**项目应用建议：**目前V0.1 REVIEW文档应显示“待评审”，不能仅因为生成文档或画了图就显示“冻结”。每次范围裁剪记录旧口径、理由/证据、影响项、批准人和日期；已批准版本不能被浏览器中的模拟点击改写。

### 2.3 双向追踪不是只有PRD到页面的单向链接

SEBoK要求管理需求基线、沟通、变更、状态及其与系统工程工件的双向关系；管理覆盖需求来源、分配、接口以及验证/确认工件。[SEBoK Requirements Management](https://sebokwiki.org/wiki/Requirements_Management)

**项目应用建议：**一项设备状态应能回查“为什么需要”，一条PRD要求应能检查“由谁、在哪个设计/交付项、用什么证据实现”。多对多映射是正常的：一个状态可支持多个需求，一个需求也可能跨设备、小程序和后台。空映射需要显式暴露，不能统计为覆盖完成。

### 2.4 验证、确认与最终交付接受分别回答不同问题

NASA产品实现章节区分产品验证（是否符合规定需求）和产品确认（在预期环境是否满足用户期望）；验证可用测试、分析、检查或演示等方式提供客观证据。[NASA §5 产品实现](https://www.nasa.gov/reference/5-0-product-realization/)

**项目应用建议：**采用V模型的配对思想，而不规定单次瀑布顺序：PRD/使用场景对应端到端确认，系统/接口需求对应集成验证，设备规则对应组件验证。规划验收方法应从需求定义时开始。团队接受11月15日展示是项目批准活动，不能与测试通过混为一谈；可点击原型只能作为行为讨论或交互确认材料，不能证明算法、摄像头覆盖和目标板性能。

### 2.5 状态转移需要事件、守卫与动作；独立条件可并行

W3C SCXML规定，带事件和条件的转移要同时满足事件匹配与条件成立。它支持复合状态、同时活跃的并行状态区域、进入/退出执行内容和历史状态；并行区域不等于多线程实现。[SCXML §3.1、§3.4、§3.5、§3.8、§5.9](https://www.w3.org/TR/scxml/)

**项目应用建议：**统一显示 `事件 [守卫] / 动作 → 目标状态`，如 `倒计时结束 [隐私允许且准备仍有效] / 重置动作半周期 → 识别中`。网络、隐私和结果同步作为独立状态维度，避免把“离线”当成必须终止运动的一张页面。暂停恢复前必须检查站位并清除未完成动作周期；结果应区分待保存、保存失败、已本地保存和待同步。此处是SCXML语义的设计参考，不宣称当前HTML实现了SCXML处理器。

### 2.6 架构图要按问题和受众分层

C4官方把系统上下文、容器、组件、代码作为不同缩放层次，并提供动态和部署图；不要求使用全部层次。[C4 Diagrams](https://c4model.com/diagrams)

**项目应用建议：**评审先显示儿童/家长/老师与设备、小程序、后台的边界，再显示识别、会话、存储与同步职责，以及一次任务/结果的数据流。C4的“容器”是应用或数据存储等架构单位，不是外壳或Docker的专用同义词；ID/硬件布局应另用物理视图，不能被软件架构图替代。

### 2.7 ADR保存决策依据而非只有答案

ADR组织的模板说明采用标题、状态、上下文、决定和后果；MADR补充备选方案、利弊和决策者等信息。[ADR Templates](https://adr.github.io/adr-templates/)

**项目应用建议：**示范媒体、显示方案、摄像头角度、存储和输入方式分别记录一个决策。待决问题应显示选项、约束、证据缺口、受影响需求/状态/器件和确认期限；未选择时维持“待确认”。已接受决定被修改时保留旧记录并建立替代关系。

## 3. 对现有材料的诊断

已读取[PRD对应矩阵](../planning/PRD到1115演示功能对应矩阵_V0.1_20261010.md)和[设备端需求基线评审稿](../requirements/设备端需求基线_评审稿_V0.1_20261010.md)。两份材料已具备稳定追踪ID、范围状态、异常规则和关键待决入口，适合先建立轻量映射，而非另写一套脱离来源的需求。

- R编号是本次追踪ID，不是PRD原生ID；工作台需同时显示章节和原有要求。
- 11月15日核心建议/待裁剪与PRD第一版/后续定位应保留两个维度。七动作、家校协同的本次范围不能自动定为延期。
- 设备基线状态为REVIEW；没有真实目标板通过证据。统计只能表示条目数/已有映射，不能称研发完成率。
- 已同步任务离线识别是既有需求。技术实现方式仍需评审，不应再次询问产品是否要求。
- 动作教学媒体与儿童采集影像是不同数据类别；前者缓存讨论不能改变后者不持久化的边界。

## 4. 建议工作台的四个视图

|视图|核心问题|建议呈现|评审动作|
|---|---|---|---|
|范围与追踪|PRD哪些要求进入本次展示，为什么？|来源→R→设备FR/S→状态→验收；筛选模块、范围、未决、缺映射|逐项确认纳入/延期/待决，记录差异|
|设备状态|每个事件在什么条件下改变行为？|主流程、暂停/异常、事件/守卫/动作表；隐私/网络/同步独立条件区|验证可恢复路径和禁止转移，核对设备输出|
|决策与影响|一个未决项会改变哪些设计？|问题→选项→需求/状态→硬件/架构影响；Owner、证据与截止|用证据做决定，确认后更新受影响工件|
|交付与验收|11月15日到底交付什么，如何证明？|交付项→环境/版本→判定准则→方法→证据→评审结果|补Owner和阈值，核查真实证据及端到端一致性|

四视图是本项目裁剪建议，不是某来源规定的标准图集。它们应由同一组ID和关系驱动；工作台为现行文档导航/评审层，不替代其权威性。

## 5. 最小数据字段与呈现规则

建议需求条目包含：ID、来源章节/链接、需求原文摘要、父/子关系、11月15日范围建议、审批状态、设备/小程序/后台责任、关联状态/决策、验收准则、证据和Owner。未定义的Owner、阈值、批准人、时间或证据显示“待补/未提供”。

状态条目包含：进入条件、进入/退出行为、设备显示/语音、事件、守卫、动作、目标状态、保护规则和关联需求。决策条目包含：状态、上下文、选项、影响、证据、决策者、日期、后果及替代关系。

必须分开三条状态轴：

1. 需求审批：草案→评审→批准→被替代。
2. 实现进度：未提供证据/计划/进行中/已实现。
3. 验证结果：未执行/通过/失败/阻塞，绑定版本、环境和证据。

初版浏览器可做筛选、关系回查和交互演练；任何模拟值/按钮均标注“演练”。演练成功不得自动改变上述审批、实现或验证轴。对无映射的条目保留完整列表，避免“只看演示主链路”掩盖PRD遗漏。

## 6. 下一轮评审的具体顺序

先确认11月15日范围及差异，再确认设备输入/显示/媒体等影响主链路的决策；随后逐节点核对正常、暂停、隐私、离画、保存失败和离线补传。每个纳入功能补Owner、可判定验收条件和目标环境。最后评审架构/硬件承担能力与接口，按版本记录批准。正式需求或方案变化依仓库“旧口径—新证据—建议修改”规则执行。

本报告只提供方法和应用建议；未冻结屏幕、触控、67 × 92 mm最终尺寸、算法方案或11月15日功能名单。
