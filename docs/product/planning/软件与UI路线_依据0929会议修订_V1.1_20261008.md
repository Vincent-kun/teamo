# 软件与 UI 路线：依据 9 月 29 日会议修订 V1.1

复核日期：2026-10-08。来源：本地原始《智能纪要：项目开发相关工作安排讨论 2026年9月29日(1).docx》，并对照同目录《会议分析_2026-09-29.md》。原始纪要由 AI 生成并自带准确性提示；以下是据纪要修订的规划建议，不代表范围已正式签核或工作已完成。

## 1. 本次修正

此前新增路线只核对旧八周台账，遗漏了本次会议。当前交付应以会议提出的 **2026-11-15 展示、约一个月开发** 为约束，不再默认 W5/W6 分别交付单动作/三动作。旧八周甘特图是任务与风险池，不能原样作为本轮执行排期。

会议直接明确：

- 全链路 MVP：APP/小程序、后台、设备屏幕交互、实体原型机。
- 节后启动，四人核心团队，新增成员与前后端工程师作为支持资源；人数不等于已确认全职容量。
- 先开发板验证，不急于定制电路板；胶囊结构可用 3D 打印。
- UI 简约方向，产品提供 2–3 套配色/风格供张羽西讨论；确认后再形成最终设计。
- 设备功能先梳理清楚，再做 UE；小夏整理平台需求，明确后端优先功能。
- 每日在企微同步进度，加强各环节对齐，避免重复开发。

尚未明确：本轮动作数量与算法验收阈值；Android/iOS 是否与小程序同轮交付；学校能力、AI 分析和体态是否必须进入此次展示；确切启动日；触控/按键方式；各支持人员实际投入。圆屏是会议倾向，但待办仍要求圆/方最终结论。参考尺寸“62×797”不可据此设计；硬件报价“2000以内/1800询价”的费用组成也需明确，原文不足以认定仅为单台 BOM。

已有会议分析中“10-09启动”、固定屏幕参数、部分人员身份、尺寸纠正和费用分类含推断；本轮不把这些推断当作已冻结事实。会议启动安排不能直接证明台账任务已完成，不能据此批量回填实际完成日期。

## 2. 截止日期驱动的执行建议

以下日期是为赶上 11 月 15 日倒排的建议检查点；若实际启动与资源不同，须重新评估可行性。

| 时间 | 软件重点 | UI 重点 | 检查点 |
|---|---|---|---|
| 10/09–10/12 | 确认展示范围、责任人、主链对象与协议；目标板/屏幕/算法冒烟验证；建立小程序与后台最小工程 | 梳理设备功能、双端主链与异常线框，准备2–3套简约风格方向 | 主链范围可执行，硬件可获得；屏幕/输入未定处有备选；风格进入讨论 |

10/09 是建议开始日，不是会议原文确认的启动日。10/08 至 11/15 约 38 天；这不等于拥有 38 个完整开发工作日，需扣除不可用时间与协调成本。

## 3. 最小交付主链与范围取舍

建议首先确保：家长绑定/选择儿童 → 创建任务 → 设备确认 → 入镜 → 倒计时 → 真实识别计数 → 暂停/恢复 → 可靠保存 → 后台接收 → 家长查看。设备自主运动是否并列展示由范围评审确认。

原台账中的开合跳可作为首个真实动作候选；会议本身没有冻结该动作或三动作要求。新增动作采用同一会话接口，在单动作通过后接入，不保证第六周自然完成三动作。学校端、原生三端、AI分析、体态、多皮肤均保留原需求与承诺记录；是否进入此次展示须明示评审，不能静默删除，也不能因演示页已有入口就认定必须一并实现。

本地现有 UI/演示流程与素材继续复用；生产模块仍独立实现。状态矩阵和首阶段清单保持有效，优先完成与展示主链直接相关部分，评审、UI和工程并行，避免完整设计定稿后才开始编码。

## 4. 资源与风险处理

四人核心团队若各有四个完整工作周、每周40小时，仅约640小时名义容量；这是情景估算，并非已知实际投入。原台账软件相关1578h、全项目3392h不能直接装入本轮。外围工程师的可用时段、任务承接范围必须列清；导师支持不能等同实现工时。

优先确认四个执行责任窗口：产品/UI/集成、设备软件与算法接入、小程序、后台与通信；按人员能力分配，不擅自将姓名绑定未知岗位。硬件采购与结构需要明确并行承接人，不能让软件关键人员同时承担不可控工作而不减容量。算法无现成可部署实现时，是最高风险项之一，首几天就要验证，不等 UI 完成后才发现不可用。

硬件/算法延误时先保留模拟器推进，但真实能力检查点不可用模拟结果替代。11/15固定时，只能通过增加有效资源、明确减少本轮范围或承认未达成验收来处理；不能仅压缩测试期。
