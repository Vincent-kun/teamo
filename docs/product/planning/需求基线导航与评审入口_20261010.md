## 2. 此轮直接可拿去讨论的材料

1. Device Requirements：设备需求评审稿，按每条FR确认行为、状态、异常、验证及演示归属。
2. Hardware Requirements：现有硬件V2.0保持原位，结合设备需求§5的参数映射和统一决策台账评审；未发送到外部群聊。
3. 11/15范围：以PRD对应矩阵R01–R45和S01–S25逐项决定；不把建议延期当最终决定。
4. UI/ID：只针对范围内已讨论状态细化线框与比例；媒体形态、屏幕、输入未决处明确候选。精确内部结构待关键器件及功能空间有证据。

## 3. 共同基线的完成条件

每条需求有来源、FR/R/S关联、纳入/延后决定、接口或状态、硬件依赖、验收、责任人、确认信息与证据。评审采用“旧口径—新证据—决定—影响”，特别处理像素屏与视频示范、设计包络与实际模组空间、第一版完整范围与11/15切片的差异。通过后发布V1.0需求基线；实现与验收另记，不以文档存在即完成研发。

文件已在本地整理；Git提交、推送、团队发送与签核尚未发生。

## 4. 可视化评审入口与专业方法

入口：[需求基线评审工作台](../../../prototype/requirements-review-workbench.html)。本地HTML双击打开；默认先看“一次运动怎样完成”，逐步解释用户操作、设备行为、展示范围建议和五个优先问题。详细需求、状态、决定和验收四视图保留在侧栏。专业依据见[方法研究](../design/专业需求基线与可视化评审方法研究_20261010.md)。NASA/SEBoK的追踪与变更、SCXML的事件/守卫语义、C4分层及ADR决策记录用于本项目裁剪，不宣称完整标准实现。

工作台从现有Markdown抽取45条PRD对应、12条设备FR、25个软件工作包、15项D决定及8项OPEN问题。来源映射与关联FR推导分开显示，缺直接关系仍保留。原[全软件状态图册](../../../prototype/state-design-lab-prototype.html)继续承担完整能力/职责/局部图，本页承担共同需求评审与11/15切片追踪，两者不替代。

- 需求审批、工程实现、实机验证独立；源文件尚无共同签核及实机证据，不以条目数显示研发完成率。
- 草稿编辑仅在本页内存；导出JSON后可显式导入恢复，刷新前必须导出。草稿不回写PRD、不自动接受ADR、不改变正式证据状态。导入错误保留当前草稿。
- 媒体选项按钮仅比较依赖，不能改变已经明确的离线运动或儿童视频不持久化边界。
- 视图关系是评审快照。修改来源后运行 `node prototype/build-requirements-review.mjs`；可编辑源为 `prototype/requirements-review-template.html`，派生数据是 `prototype/requirements-review-model.json`，生成HTML不手工维护第二份答案。
