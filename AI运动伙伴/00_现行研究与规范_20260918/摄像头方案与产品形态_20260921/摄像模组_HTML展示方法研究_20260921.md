# 摄像模组 HTML 展示方法研究（2026-09-21）

> 用途：指导《儿童 AI 运动伙伴摄像模组技术方案》制作成可用于立项、RFQ、PDR/CDR 和测试验收的单页 HTML。  
> 证据边界：仅采用标准组织、政府/航天机构、原厂/官方技术文档。本文给出展示与验证方法，不替代具体器件数据手册和实验记录。

## 1. 结论先行

推荐将 HTML 做成一条“决策证据链”，而不是把 Markdown 原文平铺成网页：

**使用情境 → 可测需求 → 系统架构 → 关键权衡 → 工程实现 → 验证设计 → 测试结果 → 风险与 Gate 决策。**

这条顺序同时兼顾三类读者：管理者先看到结论和风险；硬件/算法人员能下钻参数与证据；供应商可直接读取接口、包络、功耗和验收边界。页面中每个关键指标均应使用唯一 ID，并能从“用户情境”双向追溯到“设计参数、测试用例、结果和 Gate 决策”。

不建议以“Sensor—镜头—接口—功耗”的器件目录顺序开场，因为这种顺序缺少问题定义，也无法说明参数为何合理、测试是否覆盖目标场景。

## 2. 成熟工程评审结构如何转化为 HTML

### 2.1 用生命周期评审组织章节，而不是一次性方案汇报

NASA 系统工程方法将技术成熟过程拆成 MCR、SRR、SDR、PDR、CDR、SIR、ORR 等评审节点；不同节点回答不同问题。NASA 的技术评审资料也明确把 SRR/PDR/CDR、测试准备和验收评审放在不同阶段；正式过程要求技术评审用于判断对下一阶段的就绪度，并留下问题、责任和关闭计划。[NASA Systems Engineering Handbook](https://www.nasa.gov/wp-content/uploads/2018/09/nasa_systems_engineering_handbook_0.pdf)；[NASA NPR 7123.1C Systems Engineering Processes and Requirements](https://nodis3.gsfc.nasa.gov/displayAll.cfm?Internal_ID=N_PR_7123_001C_&page_name=all)

对本项目不必照搬航天流程，建议压缩成四个 Decision Gate：

| Gate | 页面要回答的问题 | 必备证据 | 决策输出 |
|---|---|---|---|
| G0 场景/需求冻结 | 目标儿童、距离、动作、光照与隐私边界是否清楚？ | 使用情境、需求树、未决假设 | 是否允许发 RFQ |
| G1 架构/PDR | Sensor、镜头、接口、电源和结构组合是否可实现？ | 架构图、FOV/带宽/功耗预算、候选料比较 | 样机组合与采购 |
| G2 设计/CDR | 电气、光学、结构、热和隐私设计是否足够完整？ | 原理图/PCB/堆叠、标定方案、风险关闭状态 | 是否投板/开模 |
| G3 TRR/验收 | 测试条件、样本、指标和停止规则是否冻结？结果是否达标？ | 追溯矩阵、DOE、测试报告、失败样例 | Go / Conditional Go / No-Go |

HTML 顶部应放一条横向 Gate 时间轴，每个 Gate 显示状态、缺口数量和负责人；点击后滚动到对应证据区。这样“讲解顺序”和“项目决策状态”保持一致。

### 2.2 需求必须双向追溯到验证

NASA 要求需求具有唯一标识、能双向追溯到上层需要；验证矩阵应至少记录需求来源、验证方法和结果。NASA 的示例还强调 requirements、design、implementation、test cases 之间的链接。[NASA Systems Engineering Handbook Appendix C/D/E](https://www.nasa.gov/reference/system-engineering-handbook-appendix/)；[NASA MSFC Systems Engineering Handbook，§3.3.2.1.2](https://standards.nasa.gov/sites/default/files/standards/MSFC/C/0/msfc-hdbk-3173_rev_c.pdf)；[NASA Requirements Validation / RTM](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695440/SWE-055%2B-%2BRequirements%2BValidation)

页面采用“需求证据卡”，字段固定为：

`需求ID → 来源情境 → shall陈述 → 设计响应 → 验证方法 → 测试ID → 当前结果 → 状态/责任人`

建议的首批需求 ID 示例：

| ID | 示例 shall 需求 | 设计响应 | 验证 |
|---|---|---|---|
| CAM-FOV-001 | 在规定距离和站位偏差内，应覆盖目标年龄段儿童全身与动作余量 | 镜头视场角、安装高度/俯仰、畸变校正 | 实景覆盖率 + 边缘关键点成功率 |
| CAM-IQ-002 | 在目标照度区间内，应输出满足姿态模型输入质量的图像 | Sensor、曝光、增益、ISP | SFR、SNR、拖影 + AI 任务结果 |
| CAM-LAT-003 | 采集至反馈的端到端延迟应低于冻结阈值 | 帧率、曝光、ISP、推理管线 | 时间戳测量，报告 P50/P95/P99 |
| CAM-PWR-004 | 运动识别状态下摄像子系统功耗应低于预算 | 电源域、帧率/休眠策略 | 稳态与峰值功耗、温升测试 |
| CAM-PRI-005 | 视频不得持久化，并应具备可感知的物理遮挡/状态 | 遮挡片、电源域、指示状态 | 断电、抓包、存储审计、误用场景测试 |

### 2.3 每个 Gate 必须是“判据”，不是会议名称

每个 Gate 卡片至少呈现：Entry criteria、要求的证据、量化 Exit criteria、未关闭风险、决策人、决策日期。推荐三态：

- **Go**：所有安全/隐私硬门槛通过，性能指标达到冻结阈值；
- **Conditional Go**：仅剩有责任人和期限的非关键缺口；
- **No-Go**：硬门槛失败，或证据不足以支撑结论。

页面不应只显示绿色“完成”；应允许查看“为什么通过”和证据链接。

## 3. 摄像系统的科学验证方法

### 3.1 先建立 Operational Design Domain（使用情境域）

摄像模组不是在实验室图卡上独立工作的。验收域应覆盖实际链路：儿童 → 空间/照明 → 镜头/Sensor → ISP → 姿态/动作算法 → 反馈。

推荐把使用情境建成可筛选矩阵：

| 因子组 | 建议水平（最终数值需由 PRD 冻结） | 主要失效模式 |
|---|---|---|
| 人 | 年龄/身高分组、体型、肤色覆盖、单人/干扰人 | 小目标、分组性能差异、误跟踪 |
| 动作 | 开合跳、深蹲、跳绳；慢/正常/快；正面/偏转 | 拖影、遮挡、周期漏计/重计 |
| 空间 | 距离、左右偏移、上下边缘、相机俯仰 | 出框、边缘畸变、像素密度不足 |
| 光照 | 低/典型/高照度、顺光/侧光/逆光、频闪光源 | 噪声、过曝、条纹、肤色漂移 |
| 外观 | 深浅衣服、宽松衣、图案、鞋袜、背景复杂度 | 肢体混淆、轮廓丢失 |
| 设备 | 冷/热机、供电状态、量产公差、不同样机 | 热噪声、焦漂、个体差异 |

这张矩阵应在 HTML 中成为“验证范围地图”：行是场景因子，列是研发/实验室/实景/量产测试；单元格显示已覆盖样本数和通过率。

### 3.2 使用 DOE，而不是随意堆案例

NIST/SEMATECH 工程统计手册建议先设定目标，再选择过程变量与水平，然后选择随机化、区组、全因子、分部因子、筛选或响应面设计；DOE 用于识别因素和交互作用，而不仅是多拍一些视频。[NIST/SEMATECH Engineering Statistics Handbook](https://www.nist.gov/programs-projects/nistsematech-engineering-statistics-handbook)；[NIST：Choosing an experimental design](https://www.itl.nist.gov/div898/handbook/pri/section3/pri3.htm)

建议分三层：

1. **筛选试验**：距离 × 照度 × 动作速度 × 方位 × 背景复杂度，用分部因子设计找主效应和高风险交互；随机化执行顺序，按儿童/设备做区组。
2. **边界加密**：对最低照度、最大距离、画面边缘、最高动作速度等风险边界追加水平和重复测量。
3. **确认试验**：使用未参与调参的锁定测试集，在代表性样机和热稳态下复现；输出置信区间而非只报平均值。

测试矩阵每一行至少记录：条件组合、样机/固件/模型版本、随机种子或顺序、样本量、原始数据位置、指标、置信区间、判定。训练集、调参集和最终验收集要隔离。

### 3.3 标定与畸变：不仅显示“校正前后”

OpenCV 官方标定模型使用相机内参和径向/切向畸变参数；推荐从不同位置和姿态采集足量标定板视图，并以重投影误差评价拟合。官方教程指出实践中通常需要至少约 10 张高质量、位置不同的标定视图；交互式工具同时检查置信区间、平均重投影误差、画面覆盖和视角数量。[OpenCV Camera Calibration](https://docs.opencv.org/4.x/dc/dbb/tutorial_py_calibration.html)；[OpenCV Interactive Calibration](https://docs.opencv.org/4.x/d7/d21/tutorial_interactive_calibration.html)

HTML 应显示四联图：

1. 标定板角点覆盖热图（中心和四角是否被覆盖）；
2. 原图/去畸变图拖动对比；
3. 全局及每帧重投影误差分布；
4. 边缘 ROI 中的关键点误差/动作识别变化。

注意：低重投影误差只说明模型拟合良好，不等于 AI 任务必然更好；因此必须把几何指标和下游关键点/计数指标并列。超广角若普通针孔模型残差呈系统性分布，应比较 OpenCV fisheye 模型或更合适的标定模型，而不是仅增加高阶参数。

### 3.4 成像质量：客观实验室指标与任务指标分层

建议分成三层，防止用单个“画质分”替代系统结论。

#### A. Sensor/模组基线

EMVA 1288 是机器视觉相机和传感器客观表征标准，覆盖响应、灵敏度/噪声、暗电流、阵列非均匀性和缺陷像素，并规定测量与报告方式；Release 4.0 增加了更一般的相机模型。[EMVA 1288 官方页](https://www.emva.org/standards-technology/emva-1288/)；[EMVA 1288 Release 4.0 General](https://www.emva.org/wp-content/uploads/EMVA1288General_4.0Release.pdf)

页面指标可包括：响应线性、时域暗噪声、动态范围、饱和容量、PRNU/DSNU、缺陷像素、温度条件。原厂 datasheet 数值与本机实测必须分栏，不能混写。

#### B. 镜头 + Sensor + ISP 的系统画质

ISO 12233:2024 规定数字相机分辨率和空间频率响应（SFR）测量方法，并明确像素数不等于分辨率，系统结果受镜头、Sensor 与图像处理共同影响。[ISO 12233:2024](https://www.iso.org/standard/88626.html)

ISO 15739:2023 规定噪声—信号和动态范围的测量/报告，并明确曝光、温度和内部降噪会影响结果。[ISO 15739:2023](https://www.iso.org/standard/82233.html)

ISO/TS 19567-2 提供加工后相机的纹理再现测量协议，可用于防止强降噪/锐化造成“图卡看起来锐、人体细节却被抹掉”。[ISO/TS 19567-2:2019](https://www.iso.org/standard/70955.html)

ISO 18844:2017 规定数字相机眩光的定义、测试图、条件和测量方法，但不替项目规定合格阈值；因此逆光/侧光阈值必须从本项目动作识别风险推导。[ISO 18844:2017](https://www.iso.org/standard/63552.html)

推荐页面展示：中心/0.7 场/四角 SFR 热图；不同照度下 SNR/动态范围曲线；色彩与曝光稳定性；暗场/平场缺陷；运动目标拖影长度。每张图必须带拍摄条件、固件/ISP 版本和样机编号。

#### C. AI 任务与端到端体验

NIST AI RMF 要求建立客观、可重复、可扩展且有文档记录的 TEVV 流程，并在数据、模型、集成和运行阶段持续验证；指标应为风险和管理决策提供可追溯依据。[NIST AI RMF 1.0](https://nvlpubs.nist.gov/nistpubs/ai/nist.ai.100-1.pdf)；[NIST AI RMF Core—Measure](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)

本产品的任务级验收不宜只报“姿态准确率”，应同时包括：

- **人体/关键点层**：人体检出率、关键点可用率、边缘与遮挡条件误差、连续跟踪中断率；
- **动作层**：逐动作 Precision、Recall、F1，混淆矩阵；
- **计数层**：每段绝对计数误差、相对误差、漏计/重计率，按动作和情境分层；
- **反馈层**：采集到反馈的 P50/P95/P99 延迟、错误反馈率；
- **鲁棒/公平层**：按年龄/身高、照度、服装、位置等分组报告，并列最差组，不用总体平均掩盖尾部；
- **失败样例层**：展示典型失败帧、条件标签、原因分类与缓解状态。

最终验收必须是“端到端”：同一条件下同时记录成像指标与 AI 指标，分析 SFR、SNR、拖影、畸变同任务性能的关系，才能决定应改镜头、曝光/ISP、模型还是交互引导。

### 3.5 验证与确认需要分开表达

- **Verification（做对规格）**：接口、分辨率、帧率、功耗、温升、SFR、标定残差是否满足冻结要求。
- **Validation（做对产品）**：真实家庭中，儿童是否在预期站位和光照下被完整看见，动作能否稳定计数并及时反馈，隐私控制是否易理解且有效。

HTML 中使用左右双泳道：左边“实验室 Verification”，右边“家庭情境 Validation”，最终在“端到端 Go/No-Go”汇合，避免只通过图卡测试就宣布产品可用。

## 4. 推荐的 HTML 讲解顺序与可视化

| 顺序 | 章节 | 讲解目的 | 首选可视化 |
|---:|---|---|---|
| 1 | 执行摘要 | 30 秒理解推荐方案、核心指标、最大风险和当前 Gate | 结论卡 + Gate 状态条 |
| 2 | 使用情境与问题 | 解释 1.5–3 m、儿童全身、室内运动等参数从何而来 | 房间侧视剖面 + 人体/FOV 覆盖滑杆 |
| 3 | 可测需求 | 把用户语言转为 shall 需求与验收边界 | 需求树 + ID 卡 |
| 4 | 系统闭环 | 展示从光到反馈的完整链路和责任边界 | 采集→ISP→推理→反馈流程图 |
| 5 | 推荐架构 | 展示 Sensor、镜头、IR-cut、FPC、SoC、电源/隐私控制 | 爆炸图/方框图 + 接口标注 |
| 6 | 参数与权衡 | 解释 FOV、边缘畸变、像素密度、低照、功耗、体积的冲突 | 多方案雷达图（辅）+ 加权决策表（主） |
| 7 | 光学与结构 | 解释安装高度、俯仰、窗口、遮挡和包络 | 尺寸剖面 + FOV 锥体 + 遮挡交互状态图 |
| 8 | 电气/带宽/功耗/热 | 证明接口和电源设计可落地 | 功耗瀑布图、数据带宽 Sankey、热路径图 |
| 9 | 标定与 ISP | 展示如何把镜头输出变成稳定算法输入 | 校正前后滑块、覆盖热图、误差分布 |
| 10 | 验证策略 | 证明测试覆盖关键场景并采用科学设计 | ODD 因子矩阵 + DOE 立方体/覆盖热图 |
| 11 | 结果仪表板 | 同屏看客观画质、AI 与端到端结果 | SFR 热图、SNR 曲线、混淆矩阵、分组箱线图 |
| 12 | 需求追溯 | 证明每个关键主张都有设计和测试证据 | 可筛选 RTM 表；点击展开证据 |
| 13 | 风险与 Gate 决策 | 明确哪些事实已知、哪些仍是假设 | 风险燃尽图 + Go/Conditional/No-Go 卡 |
| 14 | RFQ/下一步 | 让供应商和团队知道需要提交什么 | 交付清单、Owner、截止日期 |

### 页面交互原则

- 首屏只保留 4–6 个结论指标；详细参数按“管理/工程/供应商”视图筛选。
- 图表支持按照度、距离、动作、位置、年龄/身高组、样机和版本筛选；筛选条件需常驻显示。
- 所有结论数字可点击展开：测试条件、样本量、统计区间、原始记录链接、需求 ID。
- 用明确状态编码：已测、待测、推算、供应商声称。颜色不能是唯一编码，须配图标/文字。
- “目标值、原厂规格、工程预算、实测值”使用四列，禁止放在同一数字卡中混淆。
- 图表默认展示分布和最差组；平均值作为辅助，不把它作为唯一验收依据。

## 5. 建议的输出方式

### 5.1 交付物

建议输出一个可离线打开的自包含 HTML，并保留结构化数据源：

1. `儿童AI运动伙伴_摄像模组技术方案_可视化版_V0.1.html`：用于讲解、评审和 RFQ；
2. `camera_requirements.json`：需求、来源、状态、验证方法；
3. `camera_test_results.json`：条件、样机/版本、指标、置信区间和证据链接；
4. `assets/`：图卡照片、标定前后、结构示意和测试图；若必须单文件交付，再将必要的小图内嵌。

当前若没有实测数据，HTML 必须显式标记为“方案基线/待验证”，并使用示意图，不制造看似真实的曲线。页面中预留结果组件和 JSON schema，待样机数据到位后直接替换。

### 5.2 讲解节奏

- **5 分钟立项版**：1 → 2 → 5 → 6 → 13 → 14；
- **20 分钟 PDR 版**：1–10 → 12–14；
- **工程深审版**：完整顺序，并逐条打开 RTM 与测试证据；
- **供应商 RFQ 版**：2 → 3 → 5 → 7 → 8 → 10 → 12 → 14。

页面顶部提供“讲解模式”切换，隐藏不相关章节，但共用一份数据，防止多个版本口径漂移。

### 5.3 页面完成判据

- 任一关键参数均能回答“来自哪个情境/需求”；
- 任一 shall 需求均有唯一 ID、验证方法、测试条件与状态；
- 任一通过结论均能展开看到版本、样本量和证据；
- 风险、假设和未测项不被绿色指标遮蔽；
- 图卡画质与真实动作 AI 结果分层呈现，又能在端到端视图关联；
- 隐私要求与性能要求同级进入硬 Gate。
