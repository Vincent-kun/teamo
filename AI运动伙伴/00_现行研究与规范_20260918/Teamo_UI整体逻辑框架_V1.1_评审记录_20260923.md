# Teamo UI 整体逻辑框架 V1.1｜逻辑评审记录

> 日期：2026-09-23  
> 评审对象：`D:\下载\Teamo_最新UI整体逻辑框架_V1.1_20260923.md`  
> 评审范围：产品逻辑、双端职责、状态完整性、功能真实性、硬件约束与前期讨论一致性  
> 说明：源文件为 Markdown 逻辑框架，不是可操作产品或完整视觉稿，因此本次是文档逻辑评审；无法进行基于真实界面截图的视觉、动效和无障碍审计。

## 1. 总体结论

V1.1 已经从“页面列表”进化为“多入口 → 统一 Session → 异常恢复 → 双端结果”的系统框架，方向正确，约有 **70%–80% 可保留**。它最强的部分是双端职责、儿童自主权、Camera 隐私、离线闭环和结果真实性。

但目前仍不能直接进入高保真 UI，原因不是页面缺少，而是四个产品层决策尚未闭合：

1. **硬件尺度出现重大冲突**：`60×90 mm + 1.8 inch` 与 `180×235×150 mm + 4 inch` 对应不同观看距离、摆放方式、声学、电源和 Camera 几何；
2. **成长宠物被整体放入 P2**：这会让 MVP 退化成运动计数器，无法验证“长期陪伴”的差异化；
3. **4G 和云模型只有连接描述，没有完整服务状态与降级逻辑**；
4. **排行榜、模块化底盘和未来移动交互完全缺席**，现在不必实现，但必须预留产品与系统边界。

建议：保留 V1.1 的 Session 主干，先修正产品架构，再进入 UE。

## 2. 可直接保留的强项

### 2.1 双端职责清楚

- 家长端承担安排、理解、支持和管理；
- 儿童硬件承担真实运动过程；
- 家长不能查看实时 Camera、逐帧动作和实时次数；
- 儿童可以开始、稍后、跳过、暂停、恢复和求助。

这与“家长付费、儿童使用”的权力平衡一致。

### 2.2 一条 Session 主链正确

四种入口复用同一运动 Session，避免每种触发建立一套状态机。`FRAMING → READY → COUNTDOWN → ACTIVE → COMPLETED/ENDED` 的主干清楚，适合作为产品、算法、开发和测试的共同语言。

### 2.3 状态真实性原则成熟

- 先本地保存，再播放完成动画；
- 网络断开不影响计数和完成；
- 家长端只显示粗粒度状态；
- 求助不自动打开 Camera；
- 提前结束保留真实结果。

这些规则应成为不可回退的产品基线。

### 2.4 设备端三种 UI 模式合理

`Face Mode / Sport Mode / Near Interaction Mode` 能解释同一块屏在不同距离和注意力条件下如何变化，比按页面机械拆分更适合硬件端。

### 2.5 泳道表达适合研发协作

家长 App、儿童设备、设备本地能力、云/后台四层泳道可以直接映射责任和验收条件，应保留。

## 3. 必须修正的问题

### P0-1：硬件尺寸与屏幕逻辑冲突

V1.1 第 19–21 节提出：

- 约 `60×90 mm`；
- 掌心大小；
- 约 `1.8 inch` 屏幕。

但现有工程推演基线是：

- 落地摆放；
- 约 `180×235×150 mm`；
- 约 `4 inch / 720×720`；
- Camera 光心约 `195–210 mm`，上仰约 `12°–18°`；
- 1.5–3.0 m 运动距离。

这不是尺寸微调，而是两条产品路线：

| 路线 | 小型掌心主体 | 落地运动伙伴 |
|---|---|---|
| 运动中观看 | 主要依赖声音，屏幕只做状态点 | 远距数字、站位和角色均可承担 |
| Camera | 低机位/FOV压力大，容易被装饰遮挡 | 可抬高 Camera 并留稳定底座 |
| 4G/电源/声腔 | 空间非常紧张 | 有合理结构包络 |
| 未来轮式底盘 | 主体轻，易扩展但重心/接口困难 | 核心机身和底盘更易模块化 |
| 角色存在感 | 更像小配件/桌宠 | 更像现场运动伙伴 |

**建议**：V1.2 采用落地 `180×235×150 mm + 4 inch` 作为 EVT UI/ID 联合验证基线；掌心路线保留为成本对照，不再写成“当前最新结论”。最终冻结以 0.5/1.5/3 m 可读性、三身高组 FOV、稳定、声学和功耗测试为准。

### P0-2：首次开通缺少 4G 实名/激活与本地先启动

“扫码绑定即可完成绑定”过于理想化。消费级物联网卡还涉及设备身份、家长实名、卡激活、套餐状态、停复机和换机解绑。

建议拆成：

```text
扫码识别设备
→ 设备与账号绑定
→ 4G 实名/激活（可稍后但云能力受限）
→ 本地演示和隐私说明立即可用
→ 4G 后台驻网
→ 云服务完成后无感增强
```

不能让蜂窝驻网或云鉴权阻塞第一屏和基础运动。

### P0-3：云模型状态没有进入 UI 逻辑

V1.1 区分了在线与离线，但没有区分：

- 本地能力已就绪；
- 4G 正在驻网；
- 数据链路已建立；
- 云模型鉴权中；
- 云模型可用；
- 云模型超时/维护；
- 4G 套餐或实名异常。

这些状态会直接决定“对话为什么不能用、基础运动是否可用、结果能否同步”。不能统一显示一个“在线”。

### P0-4：摆位检测责任需要明确

家长 App 不显示画面是正确的，但摆位检测的实时反馈必须主要发生在硬件端。App 只作为首次安装辅助，显示抽象状态；不能让家长拿着手机来回看状态，破坏儿童独立使用。

### P1-1：成长宠物不应整体进入 P2

复杂养成、商城和开放聊天可以后置，但 MVP 必须至少验证：

- 宠物由真实运动事件触发表情和回应；
- 个人最好/恢复后继续等一项长期记忆；
- 完成后感受选择；
- “初识 → 熟悉”的轻量关系变化；
- 久未使用后不惩罚、不退化。

否则 MVP 只能验证计数器，不能验证产品的长期陪伴差异。

### P1-2：亲子互动优先级偏低

“亲子一起运动”在 P1，但它是家长付费与孩子使用之间的重要平衡机制。建议将“一起选择”和“共同回顾”升为 P0，亲子运动保留一条 3–5 分钟轻量 P0/P1 试点。

### P1-3：长期趋势仍然偏结果管理

趋势不应只显示次数和时长，还需覆盖：

- 自主开始；
- 暂停后恢复；
- 孩子感受；
- 亲子共同参与；
- 证据充分度；
- 一个可选择的改进建议。

不合并成总分，不推导人格、健康或同龄排名。

### P1-4：排行榜虽后置，但缺少未来护栏

P2 写“排行榜/PK”不够。需要提前规定：

- 不做公开个人总榜；
- 默认只与自己比较；
- 家庭做共同目标，不做亲子输赢；
- 同伴挑战仅限匿名、小范围、同水平、短周期、可退出；
- 无公开倒数、连续签到惩罚、付费倍率和陌生人视频 PK。

### P1-5：模块化移动扩展缺席

虽然 MVP 不移动，系统仍需预留：

- 固定/轮式底盘能力枚举；
- 机械与电气接口；
- Camera 坐标与底盘朝向；
- UI Feature Flag；
- 移动、驻车、急停、回充和校准状态；
- 运动识别期间底盘默认驻车。

### P2-1：主题颜色过早具体化

浅色/深色/跟随系统的逻辑可保留，但具体暖橙或 Lime、颜色值应在品牌和无障碍对比测试后冻结。当前可作为视觉方向，不应写成产品逻辑事实。

### P2-2：iOS 规范只覆盖单平台

如果家长端首发仅 iOS，需要明确商业决定；否则应把“iPhone 15 Pro 393×852”改为设计基准示例，并补 Android 响应式与系统权限差异。

| UI 表达 | V1.1 状态 | 评审结论 |
|---|---|---|
| 设备已收到 | 有确认概念 | 保留；必须由设备 ACK，不是服务端接收 |

## 6. 视觉与无障碍限制

Markdown 中的字号、颜色和尺寸建议尚未形成真实界面，因此只能识别风险，不能宣称通过无障碍检查。后续原型至少验证：

- 浅/深色文字与品牌色对比；
- 0.5/1.5/3 m 的数字、状态和方向图形可读性；
- 不能只靠颜色区分 Camera、网络、完成和错误；
- 儿童端语音关闭、听觉敏感和嘈杂环境下的替代反馈；
- 运动中不依赖触控小目标；
- App 动态字体、VoiceOver/TalkBack 和减少动态效果；
- 完成庆祝和宠物动画不造成闪烁或过度刺激。

## 7. 处理建议

V1.1 不应废弃。建议将其作为“Session 与双端职责基线”，在 V1.2 中完成以下整合：

1. 保留章节 0–18、22–32 的主干逻辑；
2. 重写硬件/屏幕章节，设置形态 Gate；
3. 加入 4G 激活、端云状态、云模型降级；
4. 将最小成长宠物和亲子共同回顾提到 MVP；
5. 加入排行榜护栏与模块化轮式底盘预留；
6. 把视觉色值和单一 iPhone 尺寸降级为设计参考，不作为产品逻辑。
